# 041 · Design técnico

## Rota

`app/(account)/search/page.tsx` (RSC dinâmico): lê `searchParams` dentro de Suspense, converte com `searchParamsToQuery` (valores inválidos são ignorados); `requirePersonalUser("/search?…")` preserva os filtros; compõe pets ativos e `SearchScreen`. Este faz `fetchInfiniteQuery(searchQueries.infinite(accountId, query, pets, transport))` pelo `backendForRequest`; erro conhecido de endereço vira estado serializável; `HydrationBoundary`; `SearchExperience`.

## Feature `features/search`

```
lib/searchParams.ts      searchParamsToQuery / queryToSearchParams (puros, testados ida e volta)
lib/searchCopy.ts, lib/badgeLabel.ts
api/contracts.ts         listingSummarySchema (estreita badges, homeType, species), searchPageSchema
api/queries.ts           searchQueries.infinite(accountId, query, pets, transport?) (pageParam = page)
api/server/search.server.ts
components/SearchScreen.tsx (server)
components/client/SearchExperience.tsx composição client e hook da busca
components/client/SearchBar/SearchBar.tsx Onde, Chegada, Saída, Pet (pets ativos por prop)
components/client/FilterChips/FilterChips.tsx
components/client/ListingCard/ListingCard.tsx sem hooks; recebe summary + datas + pets
components/client/SearchResults/SearchResults.tsx lista, "Farejando…", Mostrar mais, vazio
```

Os pets do tutor (para o campo "Pet") vêm do prefetch de `GET /pets/me` feito na página, entregue como `{ id, name, species, size }[]` a `SearchScreen` (a feature search não importa a feature pets; a página compõe). Com conta de anfitrião, o campo "Pet" pede só a quantidade.

APIs públicas: `index.ts` exporta parser/serializer e tipos; `index.client.ts` exporta SearchExperience; `index.server.ts` exporta SearchScreen. `src/features/pets/index.ts` passou a exportar `petQueries`, já existente, para a composição da página sem import de internals. `src/shared/api/errors/errorCopy.ts` ganhou os três códigos de busca. Nenhum mapa ou recurso de T8 foi criado.

`api/contracts.ts` também exporta internamente `listingSpeciesSchema`: enum Zod reutilizado pelo parser da URL e pelo resumo. É local à busca porque o OpenAPI gera string livre e importar o schema da feature pets violaria a fronteira entre features. Não foi criado outro transporte HTTP, provider, store, walker ou modelo de pets. As mensagens globais de erro continuam em shared; a microcopy de apresentação fica na feature, sem dependência de shared para features.

### Níveis de validação e limites

Unitários: parser/serializer/mapper (`lib/searchParams.test.ts`), datas (`stayRules.test.ts`) e dinheiro (`money.test.ts`). Helpers de copy/selos/erro têm cobertura funcional da composição, sem suítes artificiais que repitam a implementação. Funcionais: um teste ao lado de cada um dos seis componentes de pasta, verificando comportamento e callbacks, não classes do MUI. Integração Node: prefetch HTTP/contrato/hidratação/isolamento (`api/search.int.test.ts`), auth real da página (`page.int.test.ts`) e mock E2E. Integração DOM: SearchExperience + hook + componentes + HTTP MSW estrito em SearchResults.int.test.tsx. Storybook: sete arquivos com estados e axe habilitado. E2E: jornada Playwright simula backend; não equivale a integração com API .NET real.

Dinheiro e datas não têm E2E próprio porque são funções puras; são cobertos indiretamente pelo total e datas da busca. Componentes estruturais internos e SearchScreen são cobertos na composição/SSR/jornada. Não há integração real à API de desenvolvimento nem geocodificação real nesta validação. Comandos e resultados executados ficam também em `docs/validation.md`.
